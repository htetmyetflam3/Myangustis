Keyboard, font and regional-position evidence
=============================================

Scope
-----
All 54 retained source/compiled artifacts covering the 40 pending layouts are
preserved. The existing draft's observed core coverage and gaps are unchanged.
The companion font-layout-evidence.json joins each artifact's direct keys to
actual font cmaps, plus selected context and shaping witnesses. The physical
keys, their emitted code points, the font's glyphs, and a PDF subset's bytes
are separate things; this is not a decoder or a PDF-byte map.

Font declarations are metadata, not proof of the historical font file used.
Of the 54 artifacts, 32 declare families for which local candidate faces were
compared; 2 declare Ours-Unicode, which was not found among the local fonts;
20 have no nonempty declaration in the examined artifact. Source and compiled
artifacts are counted separately, not treated as 54 independent keyboards.

ZawCode and Zawgyi L: actual key sequences
------------------------------------------
The pinned ZawCode source declares TharLon; Zawgyi L declares Zawgyi-One.
These are final outputs of source-compiled layouts replayed through the pinned
KeyMagic engine from empty context. Each letter denotes a US-layout key;
uppercase means Shift. Code points, not rendered text, are shown.

Keys   ZawCode source output                    Zawgyi L source output
uU     U+1000 U+1037                           U+1000 U+1095
us     U+1000 U+103B                           U+1000 U+103A
uG     U+1000 U+103D                           U+1000 U+103C
uK     U+1000 U+102F                           U+1000 U+1033
uF     U+1004 U+103A U+1039 U+1000             U+1000 U+1064
ju     U+1000 U+103C                           U+107E U+1000
au     U+1000 U+1031                           U+1031 U+1000

For these samples, HarfBuzz shaping with the declared candidate faces also
records the resulting glyph names and positions in the JSON. For example,
ZawCode's uU shapes as TharLon ka + aukmyit; Zawgyi L's uU selects Zawgyi-One
ka_Myanmar + dot-below-3_Myanmar. These are observations for specific files
and a modern shaper, not proof of every environment's rendering.

Same numeric code point, different font glyphs
---------------------------------------------
Point   TharLon cmap glyph         Zawgyi-One cmap glyph
103A    asat.dot                   ya-semivowel_Myanmar
103C    ra.med.dot                 wa-semivowel_Myanmar
1033    mon.ii.vow.dot             u-vowel-tall_Myanmar

For example, U+1095 is assigned the Unicode name MYANMAR SHAN DIGIT FIVE and
maps to TharLon's sd.five, but Zawgyi-One maps it to dot-below-3_Myanmar.
The examined Myanmar3 2011 font has no U+1095 entry in its best cmap. The
Zawgyi font's intended glyph meaning must not be inferred from the Unicode
character name. Cmap entries and glyph names alone do not prove full shaping.

Regional positions and font gaps
--------------------------------
The retained PaOStandard source maps comma to U+AA7B and period to U+108F;
the retained PaOh source maps comma to U+108F and Shift+comma to U+AA7B.
Both sources declare Myanmar3. The two examined generic Myanmar3 files lack
these entries in their best Unicode cmaps. The separately named local
Myanmar3 PaOh face, Padauk and Pyidaungsu all contain them. That is evidence
of available candidate coverage, not proof that any was historically used or
that every contextual rendering is correct. The region-specific Myanmar3 PaOh
face is not an exact match to the source's Myanmar3 declaration.

The retained mm3std source maps Shift+minus to U+1035. The two examined
Myanmar3 faces and Myanmar3 PaOh lack that cmap entry; Padauk and Pyidaungsu
contain it. Do not discard the layout or replace its observed gap status.

Two local files both identify themselves as Myanmar3 version 1.358, but they
have different SHA-256 hashes and tables. For the myWin source's uF output,
the examined 2011 file produces a .notdef glyph with the recorded HarfBuzz
defaults; the multi-os file produces different glyphs without .notdef. The
reason and behavior on other rendering engines are unverified. Names and cmap
coverage alone do not establish correct rendering.

Source/binary caveat
--------------------
All direct key outputs in the four contextual fixtures were replayed against
the saved drafts. The pinned compiler issued a non-fatal unrecognized-option
warning when the myWin source fixture was built; its effect is unverified.
For ZawCode, 96 of 9,025 two-key final outputs differed
between our compiled source and the separately supplied compiled artifact in
this probe. For example, ]u produced U+0075 from the source and U+0075 U+0075
from the supplied binary. The engine reported an unknown opcode for that
binary, so the cause and behavior on other KeyMagic versions remain unverified.
The artifacts remain separate; do not assume the two layouts are identical.

Legacy fonts and outstanding evidence
-------------------------------------
The reference Wwin_Burmese and WinInnwa fonts have no U+1000..U+1021 entries
in their best Unicode cmaps. Unicode-output keyboards such as myWin therefore
cannot be treated as an established original WWIN keyboard or as a legacy
byte encoding merely because key positions resemble one another. No retained
layout has yet been verified as the original WWIN keyboard.

A bounded cross-format example: ZawCode key u emits U+1000, which the examined
TharLon cmap calls ka. In the genuine book1 PDF, the user confirmed subset
byte 0x17 as က in 17 25 = က္က. The PDF's ToUnicode bridge maps that byte to
U+0075; its outline closely matches the actual WinInnwa font's U+0075 glyph
(normalized distance 0.00603, matching contour topology). This joins evidence
for one glyph, but does not prove the PDF's physical key, a universal encoding,
or an entire layout. The subset byte 0x17 is not the font code U+0075.

The examined MS-HEAVY and MS-MOOM Type 1 faces have custom 256-slot encoding
arrays, not Unicode cmaps. Their slots, a keyboard's physical keys and PDF
subset bytes cannot be joined by number alone. An original dated document or
recorded keyboard example is still needed to establish their actual input and
rendering relationship. The MS and Wwin reference font files were inspected
locally, not redistributed; TextTools and converters were not executed or
integrated. No parser, detector, scoring, decoder, or existing layout changed.

Reproduction
------------
font-layout-evidence.json identifies all font and keyboard hashes, per-key
cmap results, HarfBuzz output, version details and limitations. Run
compare-font-layouts.py with fontTools and uharfbuzz installed; use --help for
optional external font paths and the KeyMagic probe/compiled-source fixtures.
The pinned engine revision and keyboard source URLs are in the JSON and
sources.json. Build font-layout-probe.cpp against that separately fetched
KeyMagic engine using the command in the file; it models printable US keys and
a simple host passthrough, not every platform input method.

For contextual fixtures, compile the four named .kms sources with the pinned
KeyMagic compiler after removing only @ICON lines from temporary copies; keep
the Zawgyi source's zg-smart.kms include beside it. Do not edit the originals.
Name the four compiled copies as listed by --help. Fixture hashes record the
exact bytes used, and a second hash zeroes a variable v1.5 header padding byte.
For the complete report, the external fonts and original pinned keyboard
collection must be supplied locally; without them the script records missing
inputs rather than guessing. Upstream engine/font rights still apply.
